# Ark 通用模拟底座需求

当前目标是全量重建底层抽象，形成可创作、可替换规则、可解释计算的通用模拟底座。干员、敌人、技能、Buff、状态机和关卡均以内容定义接入；底层每类数值计算和行为策略均通过公开契约替换。明日方舟规则位于预设包，0-1 保留为首个官方关卡验收场景。

本版由用户在阶段一原型之后提出，替代原先围绕有限干员逐步拆分旧实现的架构目标。最新设计见 [ARCHITECTURE_V2.md](ARCHITECTURE_V2.md)，创作接口见 [CUSTOM_CONTENT_V2.md](CUSTOM_CONTENT_V2.md)，机器可读契约见 [V2_RULE_CATALOG.json](V2_RULE_CATALOG.json)。独立 V2 内核、规则运行时、编译与领域执行已按这些契约落地，实际能力及未实现项见 [V2_IMPLEMENTATION.md](V2_IMPLEMENTATION.md)。阶段一运行结果仍属于历史模型证据。

## 交付目标

新底座独立实现时间、状态、事务、事件、随机数和回放基础设施；领域模块组织能力、Buff、资源与空间流程；规则运行时执行表达式、计算图和算法提供器。新执行路径不以旧类为基类，不复用旧规则执行器，也不在缺失能力时自动切回旧引擎。

内核不认识官方干员 ID、精英化、固定 30Hz、固定伤害保底、固定属性层、固定 SP 恢复方式或固定技能类型。预设提供这些游戏规则，内容包描述具体对象。首版按关卡完善游戏内容，不要求一次性覆盖全部游戏机制。

## 核心功能需求

| 编号 | 需求 | 验收方式 |
|---|---|---|
| R01 | 任意命名空间 ID 的自定义干员、敌人、装置和召唤物 | 无需修改内核即可创建官方库不存在的单位 |
| R02 | 常见技能通过激活、目标、时间线、效果和事件组合 | 一个自定义多段技能不需要新增专用角色类 |
| R03 | 自定义 Buff 的数值、触发、叠层、周期和清理 | 同一 Buff 定义在不同叠层规则下产生独立预期 |
| R04 | 每类数值计算具有有类型的公开接口 | 所有执行中的业务数值都能定位到计算 ID、规则和版本 |
| R05 | 支持表达式、计算图和 Python 提供器 | 常见公式用配置，复杂算法可单独替换 |
| R06 | 可替换完整规则集及局部规则 | 同一场景用两套规则集运行；单个技能只覆盖指定阶段 |
| R07 | 可替换属性成长、叠加、伤害、治疗、资源、费用、冷却与量化 | 修改这些算法不编辑内核和无关领域模块 |
| R08 | 可替换寻路、索敌、范围、阻挡、弹道、位移和状态转换 | 选择策略变化会体现在可解释轨迹中 |
| R09 | 规则绑定有明确所有者、作用域和冲突处理 | 来源规则、目标规则、组件规则与场景规则不被隐式混用 |
| R10 | 按场景和编队的传递依赖加载内容及提供器 | 未引用的游戏内容不进入本场运行时；动态引用有明确约束 |
| R11 | 指令校验、资源支付与能力启动原子执行 | 非法操作不扣费、不产生部分任务；同时间操作顺序稳定 |
| R12 | 逻辑时间与数值精度由配置决定 | tick 频率、量化和舍入是版本化规则，不藏在工具函数里 |
| R13 | 完整回放锁定内容、规则、插件、调度和数值配置 | 同样输入可重放，规则变化被识别为不同运行身份 |
| R14 | 计算结果能解释每个阶段 | 可查看伤害、属性和恢复结果的输入、修饰器、覆盖及中间值 |
| R15 | 静态定义只读，运行时可变状态独立 | 两场模拟不共享 Buff、资源、状态计时器和随机数 |
| R16 | JSON 与 Python Builder 走同一编译流程 | 两种作者入口生成相同语义，校验结果一致 |
| R17 | schema 驱动的依赖说明和公式试算工具 | 创作者在运行前可定位缺失引用并预览计算结果 |
| R18 | 0-1 和自定义合成场景使用同一底座 | 不通过专门的 0-1 引擎或硬编码白名单满足验收 |

## 数值自定义范围

开放范围包括属性成长及养成，修饰器每层与层顺序，伤害和治疗整条结算管线，HP/SP/费用及任意自定义资源，部署和撤退，技能 CD、前后摇与重复，Buff 周期和叠层，位置、速度、力量和弹道，目标评分与阻挡容量，波次、漏怪、死亡、复活、评分和终局。

数值常量、单阶段公式、整条计算图和复杂提供器均可以替换。接口开放与具体算法实现是两件事；没有实现的必需契约会使场景编译失败，不能以空处理器通过。

首版不需要同时实现所有数值后端或热修改方式。已执行的计算必须明确采用 NumericProfile；战斗中切换规则作为独立能力验收，默认编辑在下一场模拟生效。

## 自定义内容的体验要求

常见创作只编辑内容包中的 JSON：单位基础属性和资源、能力激活和效果、Buff 与状态图、规则公式与参数。官方内容和用户内容使用相同定义模型。成长、天赋、装备和多资源能力不受固定精零、零信赖或单技能槽限制。

复杂机制允许增加独立 Python 模块并注册契约，但调用只读上下文和通用变更意图。增加一个新算法不得要求修改贯穿所有角色的控制函数。后续编辑器通过 schema 生成，首版先交付校验、依赖说明、公式试算与运行接口。

## 首个里程碑

先完成合成场景：自定义单位有 HP 与 energy，自定义技能支付能量、增加属性、多段伤害并在命中后回复资源。场景可以切换减法减伤与另一种公式，改变恢复和攻击间隔规则，并解释结果和重放。

随后以明日方舟预设导入 0-1，核查两类敌人、士兵 DEF=30 覆盖、等待检查点、路线、部署、攻击、技能、漏怪与终局。原有夜刀与克洛丝模型样本作为参考输入，新版重新验证。客户端版本和真实同帧记录仍需固定，内部重复运行一致不能替代游戏对照。

## 支持与验收状态

分别记录底座契约状态、内容依赖状态和真实游戏证据。规则至少区分已声明、已实现、模型验证和外部验证；场景必须说明使用的包、规则、插件、数值和调度版本。

全部底层重构的判定是：新运行路径独立于旧引擎；没有角色 ID 分支和固定游戏公式；创作样例及两套规则切换通过；计算轨迹完整；0-1 与自定义场景使用同一架构。全游戏内容覆盖继续按关卡逐步推进。
