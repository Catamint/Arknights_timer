# Ark 模拟器需求

当前目标是建立一套通用、易修改、按关卡逐步验证的明日方舟战斗模拟器。首个基准关卡已由用户确定为 **0-1，`level_main_00-01`**。先完成它在明确编队范围内的全部战斗机制，再添加干员与关卡；不再将一次性覆盖全部游戏机制作为首版目标。

本文是后续改造的需求依据，技术方案见 [架构设计](ARCHITECTURE_STAGE1.md)，首关范围与验收见 [0-1 实施计划](../LEVEL_00_01_PLAN.md)。现有代码作为迁移基线，其行为尚需重新验证。

## 交付范围

第一阶段交付一个可完整运行、可回放操作、可检查状态、可解释失败原因的 0-1 战斗环境。完整性限定为固定的数据版本、难度、关卡规则和已声明支持的干员及养成配置。关卡可加载、某个脚本获胜或全部代码测试通过，均不能单独作为与游戏一致的验收。

首关应覆盖从初始化、波次调度、全部敌人出现、交战与漏怪到终局的全过程。剧情画面、音频与菜单不属于模拟画面范围；剧情或教程若影响战斗暂停、指令或触发条件，则必须通过明确的控制输入表示。

首批模型实现已依次接入夜刀、克洛丝、芬和芙蓉，限定精零、零潜能与零信赖、无模组。模型回归样本固定夜刀 30 级和克洛丝 40 级、技能 1 级。用户确认了首关和改造方向；这些配置作为当前开发基线，真实游戏验收的版本和样本仍需固定。

## 功能需求

| 编号 | 需求 | 验收方式 |
|---|---|---|
| R01 | 指定关卡、服务器、数据版本、难度与编队创建一场战斗 | 初始化记录可导出，相同输入可重新创建 |
| R02 | 正确合并敌人数据库、等级数据和关卡专属覆盖 | 0-1 士兵的关卡 DEF 覆盖值 30 生效，不被默认表值覆盖 |
| R03 | 根据关卡和编队的依赖加载状态机、能力、Buff、弹道与环境规则 | 加载报告可列出本场实际依赖；无需导入无关活动管理器 |
| R04 | 加载前识别缺失定义、缺失处理器与未解析动态引用 | 报出关卡、引用来源、所缺能力与影响路径；该配置不进入已验证状态 |
| R05 | 通用敌人行为可复用，个别敌人的状态和阶段可单独扩展 | 新敌人优先通过定义与组件组合接入，特殊行为落在独立模块 |
| R06 | Buff 条件、属性修饰、周期、叠层、来源与生命周期有统一语义 | 多来源 Buff、到期与解除有独立预期测试和正确 tick 日志 |
| R07 | 部署、撤退、技能、暂停和单步通过统一命令入口执行 | 非法操作不改变状态；同 tick 操作有稳定顺序 |
| R08 | 移动、索敌、阻挡、前摇、命中、弹道、死亡与漏怪由逻辑时钟推进 | 对照记录能定位首次位置、目标或生效帧差异 |
| R09 | 费用、HP、SP、属性层与伤害在共用规则中计算 | 普攻、技能和 Buff 不各自复制一套公式 |
| R10 | 导出只读快照、增量事件与回放操作记录 | 快照对应确定 tick，事件含原因与关联单位，记录可序列化 |
| R11 | 战斗状态独立，静态定义可共享 | 两场战斗不共享可变 Buff、实体、状态机计时器或随机数 |
| R12 | 已验证的关卡和干员扩展不会悄悄破坏之前的配置 | 每次改动重跑受影响的关卡及其通用规则回归 |

## 按需加载的含义

加载对象是本场战斗所需的依赖闭包：关卡中的波次、分支、预部署和环境引用，加上编队选定的干员、技能、天赋、养成和可生成单位，再递归解析其状态机、能力、Buff、动作、范围和弹道引用。

按需加载不表示在执行到未知节点时忽略它。加载前检查本场潜在需要的能力；大型静态定义可以在实体首次生成时实例化。对于从黑板变量或条件分支生成的引用，必须有明确的解析规则或允许集合。未知的必要引用会使该战斗配置保持待支持状态。

普通敌人可以共享同一个行为族，但每个敌人的有效定义必须能说明其状态机、普通攻击、Buff 与数据覆盖。不要把数据库 `skills=[]` 当作没有攻击或被动行为；这些行为可能来自基础 Prefab。

## 模拟准确性与支持状态

支持状态以“关卡版本、难度、编队与养成、机制版本”组合记录。不能把一个编队下的通过结果推广成该关卡允许全部干员。

| 状态 | 含义 |
|---|---|
| 已发现 | 找到数据与依赖，尚未完整实现 |
| 实现中 | 必需规则仍缺失或有近似路径 |
| 模型通过 | 依赖完整、模型与不变量测试通过、端到端完成；尚未完成真实游戏对照 |
| 游戏对照通过 | 在固定版本与声明范围内，真实样本及关键边界场景对照通过 |
| 待重新验证 | 数据或共用规则变化，需要重跑相关对照 |

真实样本应覆盖机制行为，而不是只保存最终胜负。离散字段如出场 tick、目标、阻挡关系、命中 tick、HP/SP/费用整数事件与终局必须明确比较规则；浮点位置或数值的容差须事先记录依据，不得为了通过对照临时放宽。

## 扩展需求

新增干员需要补充数据定义、其依赖和行为验收，再在已支持关卡中验证。新增关卡需要生成依赖清单，复用已实现规则，只补新出现的敌人行为、Buff 和场地机制。新增 Boss、复杂活动或特殊模式在确有关卡需求时进入计划。

维护者应能够查到一个行为的数据来源、执行入口、运行时状态和测试样本。单个技能或敌人的调整不应要求修改贯穿所有机制的大型函数。

## 首版不纳入的内容

首版不承诺全部 454 名干员、全部历史关卡或全部活动机制；不建设账户、抽卡、基建和服务器系统；不把肉鸽等特殊模式的完整流程作为基础版本前提。AI、搜索和网页控制可以保留接口，但首关正确性优先于复杂策略和界面扩展。

## 本次文档阶段的完成标准

需求、模块边界、按需加载流程、迁移顺序和首关验收已明确；旧实现中的已知问题有归属；待确认的首批编队、养成、客户端版本和真实样本写明为待固定输入。本阶段先交付设计文档，随后实施依据这些契约推进。
