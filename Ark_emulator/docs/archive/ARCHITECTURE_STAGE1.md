# Ark 模拟器架构设计

本方案服务于 [需求](REQUIREMENTS_STAGE1.md)：先验证 0-1，再通过复用通用规则与按需加载内容逐关扩展。0-1 的通用内核、内容加载、行为族、效果模块、适配器和回放对照已落地，现有 `Simulator` 入口保持可用。具体运行方式与支持范围见 [模块化实现说明](../MODULAR_IMPLEMENTATION.md)；下面的目录图同时包含后续扩展位置，尚未迁移的内容不视为已实现。

## 模块边界

采用通用战斗内核、内容定义、关卡支持配置、验证工具和外部适配器五个边界。优先使用普通 Python 模块、明确的数据类型与小型注册表，不为首关引入新的大型框架。

```text
ark_emulator/
  core/
    battle.py             战斗状态与系统调度
    clock.py              tick 与同帧事件顺序
    commands.py           玩家指令与校验
    entities.py           通用实体及运行时组件
    attributes.py         属性层与修饰器
    damage.py             伤害和治疗管线
    movement.py           路线、寻路与位移
    targeting.py          范围、筛选与目标保持
    blocking.py           阻挡关系与容量
    abilities.py          能力启动、前摇、命中与结束
    buffs.py              Buff 实例、事件与生命周期
    events.py             事件记录与调试信息
    rng.py                随机数状态与消耗记录
  content/
    schemas.py            规范化定义与来源信息
    repository.py         按 key 和版本读取静态定义
    registry.py           处理器描述与延迟导入
    dependency.py         引用解析与依赖检查
    behaviors/            敌人状态机行为族与特殊状态机
    effects/              按领域组织的 Buff 和动作处理器
    operators/            不能由共用能力表示的干员行为
    environments/         实际需要的关卡环境机制
  levels/
    profiles/             关卡与声明编队的支持范围
    packs/                可重建的逐关数据包
  validation/
    fixtures/             固定输入、期望与真实轨迹
    replay.py             同帧操作回放
    compare.py            首次差异与字段对照
  adapters/
    api.py                公共 Simulator 门面
    live_server.py        HTTP 与 SSE
    agent_env.py          AI 动作与奖励适配
```

内核负责规则与状态推进；内容模块负责描述具体敌人、干员和机制；关卡配置负责声明本场可用内容。HTTP、UI 和 AI 通过同一个命令入口访问内核，不能各自直接修改实体列表。

## 静态定义与运行时状态

静态定义应保持只读、带版本和来源，可跨战斗共享。运行时状态只能属于一场战斗。

| 静态对象 | 运行时对象 | 关键分离 |
|---|---|---|
| LevelDefinition | BattleState、SchedulerState | 原始波次与路线不被调度游标修改 |
| EnemyDefinition | EnemyState、BehaviorInstance | 数据覆盖与基础定义独立，状态和计时器独立 |
| OperatorDefinition、BuildConfig | OperatorState | 等级、技能与范围固定；HP/SP/部署状态可变 |
| AbilityDefinition | AbilityInstance | 效果配置只读；目标、前摇、命中队列属于当前施放 |
| BuffDefinition | BuffInstance | 模板共享；来源、层数、到期与运行时黑板独立 |
| ProjectileDefinition | ProjectileState | 速度和规则固定；轨迹和目标状态独立 |

敌人有效定义按“基础库、指定等级、关卡覆盖、显式自定义覆盖”顺序生成，逐字段保留缺省、空值和零值的意义。枚举在规范化阶段统一翻译。干员定义结合当前精英化、等级、潜能、信赖、模组和选定技能生成有效属性与范围。

实体和事件 ID 建议在 BattleState 内生成，以便同样输入可以比较；对照真实记录时另设真实 ID 到模拟 ID 的映射。不要依赖进程全局计数器表达回放中的身份。

## 关卡包与依赖解析

离线提取管线将现有大表与资源索引整理成按 key 可读取的定义，并生成单关数据包。原始大表可以保留为提取输入；运行一场 0-1 不应每次解析所有关卡和全部活动内容。

加载流程为：

```text
关卡版本和编队配置
  -> 规范化关卡与有效单位定义
  -> 查找波次、分支、预部署、环境和编队引用
  -> 递归解析能力、Buff、生成单位、范围和弹道
  -> 检查动态引用与处理器是否支持
  -> 生成依赖报告与固定内容版本
  -> 创建本场运行时对象
  -> 执行 tick 和指令
```

依赖闭包要包含条件分支和运行时生成单位，不能只收录开局场上的敌人。动态黑板引用应带可解释的解析规则；无法静态枚举时由内容模块声明有效集合或验证约束。执行中发现清单之外的必要机制，记录 UnsupportedMechanic 并停止该次验证，不将其静默当成成功。

注册表保存能力 ID、版本、参数 schema、模块入口与支持状态；仅导入本场依赖的模块。加载检查与实例延迟创建可以并存：先确认所有潜在依赖可执行，再在敌人出现或 Buff 施加时创建实例。

缓存以服务器、数据版本和内容摘要为键；运行时可变对象不进入静态缓存。单关数据包应记录依赖摘要，便于共用规则或定义变化时找出需要重新验证的关卡。

## 敌人状态机

按行为族复用状态机，例如地面近战、地面远程、飞行单位、静止装置。每个敌人定义选择行为族并配置属性与能力。Boss 的特殊阶段或行为由独立状态机扩展，不给每个普通敌人复制整份类。

基础生命周期可以表示为出生、活动、退出和死亡；活动中的移动、阻挡与攻击由可组合行为管理。眩晕、冻结、沉睡、禁攻和束缚属于独立状态约束，由统一门控判断能否移动、搜索或施放，避免把所有状态组合展开成几十种状态名。

状态机接口建议保持小而明确：

```text
enter(state, context)
on_event(event, context)
tick(context)
exit(state, context)
describe_state()
```

状态转换要有明确的条件、优先级、进入和退出动作，记录转换原因及 tick。状态机提出移动或能力请求，具体伤害、Buff、费用和实体生成仍调用内核服务，避免状态机重复实现公式。

0-1 的源石虫与士兵先使用经验证的通用地面近战行为，但分别保留自身 Prefab、属性、路线与关卡覆盖。数据库技能列表为空时仍需提取普通攻击 Ability 及被动组件。

## 能力与 Buff

普通攻击和技能使用同一 Ability 执行管线：可执行检查、目标锁定、开始、前摇、生效或弹道发射、命中、结束或中断。伤害类型、范围、弹道、命中次数和帧事件来自规范化定义，不能依靠角色名字或描述文字猜测。

Buff 引擎负责施加、刷新、叠层、属性修饰、触发、到期和解除。事件处理器按属性、伤害、治疗、状态、生成、调度等领域拆分，常见节点可共享处理函数；特殊机制用独立模块。通用属性计算仅保留一份，并显式区分百分比相加与最终乘算。

每个 BuffInstance 保存来源、目标、模板版本、层数、起止 tick、周期计时器和运行时黑板。来源消失、施放中断、单位死亡、重复施加与派生 Buff 清理的规则必须显式定义。动态变量求值与有效参数检查应集中处理，避免各处理器随意猜 key。

缺失节点和近似节点在注册表中标明。一个函数返回 True 只能表示调用结果，不能作为机制正确性的证明。

## 时钟 指令与事件顺序

首关沿用 30Hz 逻辑时钟作为起点，时间内部用整数 tick 表达。动画或资源时间如何舍入到 tick 是机制契约的一部分，需要真实样本校准。公共接口的 seconds 只是转换参数。

一场战斗只有一个执行者。指令包含 tick 与同 tick 顺序号；外部请求入队，由执行者在明确边界校验和执行。非法指令不扣费、不改变队列和实体；指令结果返回执行 tick 与失败原因。

当前 tick 的系统顺序在迁移开始时保存成明确版本，并通过样本校准。需要记录出怪、移动、目标与阻挡更新、能力推进、伤害与死亡连锁、Buff 周期和到期、费用与 SP、终局各自的执行位置；不能在文档中未经对照就宣称某个顺序等同客户端。

同帧内部事件使用稳定顺序，包含原因事件、源与目标、能力或 Buff ID。循环触发超出约束时明确报告，不能静默吞掉。暂停不推进逻辑时间；单步在同一执行者内推进指定 tick，不临时向后台线程暴露“已恢复”的可写状态。

快照在 tick 完成后生成，HTTP 和 UI 消费已经发布的只读快照。实时速度只控制推进频率，不改变战斗规则。AI 的合法动作枚举复用命令校验器，避免地面与高台规则分叉。

## 验证与支持配置

单关支持配置是一个可检查的声明，以下仅为设计示例，不是已经可运行的文件：

```json
{
  "levelId": "level_main_00-01",
  "server": "cn",
  "dataVersion": "待固定",
  "mechanicsVersion": "core_v1",
  "allowedBuilds": ["nblade_baseline", "kroos_baseline"],
  "dependencies": ["ground_melee_v1", "physical_damage_v1"],
  "status": "discovered",
  "evidence": []
}
```

依赖列表由提取器生成并经人工核查，不只保留示例中的两项。验证分三层：共用规则的独立预期，固定关卡的端到端回放，真实客户端状态对照。旧测试可用于发现回归，但其中已失效的场景和错误预期必须先修订。

对照报告输出第一处差异，附带 tick、字段、预期、实际、单位映射、目标、相关能力/Buff 和随机数消耗。新增关卡按依赖关系重跑共用规则测试与受影响关卡，不要求每次运行所有历史扫描。

## 渐进迁移

| 顺序 | 从现有实现迁移的内容 | 避免的风险 |
|---|---|---|
| 一 | 将 0-1 原始数据、关卡覆盖与首批配置固定为输入样本，分类旧测试失败 | 把数据缺失误当行为错误 |
| 二 | 提取规范化定义、单关依赖与支持配置，保持旧入口作为适配层 | 重写全部内容才能运行第一关 |
| 三 | 提取属性、命令校验、快照和逻辑时钟等共用契约 | 多个接口和系统各自计算同一规则 |
| 四 | 用 0-1 两类敌人迁移通用地面状态机、Ability 与必要 Buff | 继续在大型 battle 函数堆具体敌人分支 |
| 五 | 按首批干员依次迁移部署、普攻、技能与治疗，建立真实对照 | 默认将所有现有干员标成已支持 |
| 六 | 稳定一关后迁移下一个关卡或干员，其余旧实现暂保留 | 在没有基准时一次性删除旧实现 |

旧实现与新内核可以作为两个后端短期并存，但旧输出不是正确答案。首关结果以数据契约、独立预期和真实游戏对照为依据。公共 API 的变化需要适配说明；历史模拟能力在迁移过程中标注为旧实现、待验证，不掩盖支持范围变化。
