# 战斗模拟器完整模拟差距评估

当前实施目标已调整为按关卡推进，首关为 0-1。开发范围以
[当前需求](REQUIREMENTS.md)、[架构设计](ARCHITECTURE.md) 和
[首关计划](LEVEL_00_01_PLAN.md) 为准。本文保留同次审查的数量、反例与完整性分析；
后文全量机制和特殊模式的估算是背景分析，不再作为当前交付要求。

评估日期为 2026-10-01，范围是当前工作区的 `Ark_emulator`、其依赖的数据文件与现有测试。结论是：项目已有较丰富的战斗框架，但当前仍存在影响基础结果的错误、缺失的数据依赖和明确的近似实现，尚不能认定为完整或逐帧准确的游戏模拟器。

用户提供的八个资料入口已整理到 [参考资料](REFERENCES.md)。本次完成代码审查、离线最小场景复现与一次全量回归；没有采集新的真实游戏战斗轨迹，也没有替换游戏数据或修改战斗实现。

## 完整模拟的验收目标

建议把目标定义为：固定同一服务器与游戏版本、同一关卡、同一编队养成、同一初始随机数状态和同帧操作序列后，模拟器的关键战斗状态与游戏保持一致。关键状态至少包括单位出场、位置与路线、目标选择、攻击和技能生效帧、伤害、HP、SP、费用、阻挡、Buff 与异常、阶段转换、漏怪与终局。

如果目标还包含肉鸽、保全派驻、卫戍协议和生息演算，则需要这些模式完整的输入生成、模式状态与战斗规则。现有 README 曾将这些模式的关卡排除在旧交付范围外；旧范围下的 PASS 不能直接证明新目标完成。

全游戏的画面、音频、菜单、账户、基建和服务器经济系统是更大的独立范围。本文以战斗行为完整性为主。

## 当前可确认的基线

| 项目 | 本次工作区实测 | 如何理解 |
|---|---|---|
| 核心 Python 规模 | 39 个模块，33045 行 | 有较大实现基础；代码量不代表准确度 |

| 敌方技能目录 | 1656 个目录条目 | 目录条目不是语义正确性覆盖率 |
| 范围表 | 73 个范围定义 | 部分调用路径没有使用这些精确范围 |

## 已确认的基础正确性问题

下面十项通过代码读取与离线最小场景确认。P1 表示优先修正的基础模拟问题，P2 表示公共入口、特定输入或输出契约的问题。它们是本次审查发现的下限，不是整个项目缺陷总数。

| 优先级 | 问题与代码位置 | 复现结果 | 对完整模拟的影响 |
|---|---|---|---|
| P1 | `attributes.py:70`，`mul` 层连乘 | 基础 ATK 100，两个 +50% 修饰器得到 225；本项目 `MECHANICS.md` 第 2.2 节要求百分比相加，结果应为 200 | 多 Buff、天赋和技能叠加的面板与伤害偏离 |
| P1 | `battle.py:1275` 与 `ai.py:219`，敌人普通攻击固定 PHYSICAL | `enemy_1011_wizard` 的 Ability 配置 `_damageType=2`，按项目枚举翻译为 MAGICAL；ATK 100 对 DEF 90、RES 0 的目标实际只扣 10，法术应扣 100，近战结算和远程弹道均如此 | 普通术师等敌人的攻击错误受防御影响 |
| P1 | `operator_skills.py:1536`，所有 `x-` 范围被当作全图 | 本地 `x-1` 实际有 13 格；技能选择器仍把偏移 `(-2,5)` 的远处敌人列入目标 | 范围伤害与控制误作用于范围外单位；其他技能范围还使用近似形状，未统一精确表与朝向 |
| P1 | `battle.py:3152`，基础范围取第一个非空 phase | 阿米娅 phases 为 `3-6/3-1/3-1`，实际取 9 格而精二应取 10 格；能天使取 10 格而精二应取 12 格 | 精英化范围扩展没有正确进入普通攻击索敌 |
| P1 | `battle.py:1522`，生成敌人未传入关卡 `overwrittenData` | `level_a001_01` 对 `enemy_1027_mob` 覆盖 HP 为 1850，实际生成 HP 为数据库默认的 1700 | 官方关卡专属数值与可能的行为覆盖丢失；bundle 中有 4073 条非空覆盖对象，但并非每条都已逐项验证 |
| P1 | `live_server.py:238` 与 `live_server.py:420`，多个线程直接修改同一 battle | 用屏障控制两个 HTTP 请求在部署校验之后交错，两次都返回成功，不同干员占据同一格 | 操作与 tick 缺少串行化，运行结果依赖请求交错；暂停和单步也需统一处理 |
| P2 | `battle.py:1845`，部署未拒绝已经在场的同一干员 | 同一场景将 `char_502_nblade` 部署到两格，两次都成功，在场有两个同 ID 干员 | 公共 API 允许游戏不合法的队伍状态 |
| P2 | `battle.py:4817`，胜利判定不等待 `custom_waves` | 基础时间轴为空，自定义敌人 5 秒出场；第 1 tick 已胜利，仍有 1 个待出场敌人 | 自定义场景和 AI 评估提前结束 |
| P2 | `agent_env.py:252`，合法部署动作一律使用地面掩码 1 | 纯地面地图中，阿米娅仍获得 8 个所谓合法部署动作；执行第一个返回 `not_buildable` | 策略搜索会选择非法动作，并且没有正确枚举高台部署 |
| P2 | `buffs.py` 的到期事件与 `battle.py` 的 update 调用 | 在第 2 tick 令一个 Buff 到期，记录的 `buff_expired.tick` 仍为 0 | 事件时间轴与状态帧不一致，影响调试、回放和外部消费者 |

修正这些问题时，应使用独立预期或真实配置建立反例测试，不能直接把测试预期改成当前输出。范围、属性、伤害类型和关卡覆盖应先形成共用规则，再让普通攻击、技能、召唤物和 AI 动作枚举复用。

## 测试失败与数据缺口

本次 45 项失败分布在 18 个测试文件。它们并不等于 45 个独立实现错误。

- **场景坐标与部署输入**：不少失败直接为 `not_buildable`，或在未检查部署结果后访问不存在的干员，继而发生 `IndexError`。需要核对坐标转换和地图更新后的有效部署格，明确测试真正覆盖的机制。
- **缺失数据**：关卡加载测试引用的 `level_act44side_01`、`level_act10mini_09`、`level_act17d0_03` 不在当前 bundle 中。模组与信赖的两个辅助文件不存在。预部署相关测试也未获得期望对象，需要分别检查资源文件、索引和解析结果。
- **组件合并**：Prefab 别名测试发现期望 3 个组件却得到 6 个，以及同一个 Buff 重复出现。需要审查历史与当前 Prefab 合并规则，确认去重与版本优先级。
- **行为差异**：阻挡、拉动、浮空阻挡和 PRTS 管线等测试失败，需要隔离输入后逐项核查。本次没有把每一项都归因为某段实现。
- **预期本身不可靠**：`test_operator_skill_effects` 使用“全图眩晕”的断言，而本地技能的 `x-1` 对应有限范围。当前失败与真实机制正确与否是两件事，必须依据范围表和实际战斗重新设计测试。

建议先建立数据依赖检查与可复现测试场景，使每个失败可以清楚归入输入缺失、场景失效、实现错误或尚待实测。不能通过忽略异常、跳过所有缺数据测试或恢复非法部署来追求全绿。

## 仍需要补齐的六个领域

### 数据版本与生成链路

已有静态表、Prefab 目录、Spine 事件和关卡数据，但运行结果会受缺失文件、旧索引、跨版本合并和异常回退影响。资料入口能补充输入来源，但仍需记录服务器与版本，检查引用是否解析，并正确应用关卡 `useDb` 与覆盖数据。

建议生成清单覆盖基础包、热更包、上游提交、解析器版本、输入摘要和输出数量。重要数据缺失时明确标记对应能力不可用。当前 2854 个 level 与历史 README 的 3864 之间不能直接计算“缺 1010 个当前关卡”，因为两个数据集的版本和收录范围尚未对齐。

### 基础算法与事件顺序

已有 tick、阻挡、路线、弹道、费用、SP、元素和 Buff 管线，但本次反例说明这些通用规则仍需校准。除了修正上述十项，还需建立同 tick 多事件、伤害后触发、死亡和复活、技能中断、状态解除、目标失效、弹道来源变化等顺序契约。

随机数也需外部核验：`rng.py` 的默认游标为 `(0,21)`，而仓库 `tools/ak_live_rng/rng_engines.py` 注释记录现网观测间距 31。两者存在资料冲突；这不是本次新采集的数据，也不足以直接判定初始化算法错误。逐帧复现必须比对完整随机数状态、每次消耗位置和调用顺序，不能只证明相同 seed 下模拟器自身重复运行一致。

### 能力图与 Buff 语义

能找到一个节点处理函数，不等于参数、目标筛选、动态黑板、优先级、生命周期与事件语义正确。当前 `BuffTemplateEngine._n_ModifierScaleUp` 仍直接返回 `True`；`_n_IfTarget` 对其他过滤条件近似放行；未知 `postFilter` 会回退为 ALL。这些路径可能运行成功却选择错误对象或遗漏效果。

需要按客户端实际出现的节点与参数组合建立静态清单，再用运行时分支覆盖补充。每个条目至少记录精确实现、近似实现、未实现和未验证，以及验证证据。当前模板类有 641 个 `_n_` 定义、634 个不同名称，7 个名称重复定义；Python 后定义覆盖前定义，审查时必须以有效定义为准。该数量只说明维护风险，不是机制覆盖率。

### 干员敌人和活动专属行为

部署成功、技能激活成功和没有异常，仅证明调用链可运行。还需验证每种技能、天赋、模组、召唤物、Boss 形态与活动机制的结果，包括限定目标、作用范围、阶段触发、重复命中、数值上限和结束条件。

源文件明确标注的近似仍需列入差距：`act31.py` 将污染瓦片近似作为水域，`act35.py` 将复杂的宝石传播行为标为推断实现，部分 Projectile 速度在缺表时使用启发式默认值。新增数据可以改善这些输入，但不能自动补全控制逻辑。

### 特殊模式完整状态

肉鸽、保全派驻、卫戍协议和生息演算的若干节点、计数器或 Buff 已有实现。这不能证明模式级的完整链路已经具备。若纳入新目标，需要分别验收模式输入如何生成、藏品和场外增益如何进入战斗、模式专用单位与规则、胜负与阶段条件，以及跨战斗状态如何保存。

应为每个模式定义单独的范围与测试集，避免把“存在字段或节点处理器”标成模式已完整支持。

### 真实战斗对照与可观测性

当前测试主要是本地断言与冒烟；本次没有执行真实客户端的同步对照。`test_enemy_skill_smoke_all_catalog` 的核心验收是没有捕获异常，部分缺对象路径会继续执行。`scan_unhandled.py` 只检查给定 tick 范围内实际发生的 `buff_node_unhandled`，并且吞掉关卡异常；零未处理事件无法排除未触发分支、静默失败和已注册的空操作。

因此，当前缺少的关键交付是一个独立的对照体系。项目已有操作记录、敌我实时状态和随机数读取工具，可以在验证其采样与同帧一致性后，建立固定输入的真实战斗样本。对照器应输出第一处不同的 tick、字段、模拟值和观测值，附带相关事件、目标、Buff 和随机数位置。

## 建议的补齐顺序与验收标准

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| 一 | 固定数据版本，补齐缺失依赖，分类 45 项失败，修正十项基础问题 | 必需文件和引用可检查；反例有独立预期；所有失败有明确处理结论 |
| 二 | 建立真实战斗样本、同帧操作输入与状态差异报告 | 固定输入可回放；能自动定位第一处差异；随机数状态和消耗可比对 |
| 三 | 统一属性、范围、目标选择、事件顺序和标准 Ability 执行 | 代表性近战、术师、医疗、召唤、控制、位移和 Buff 组合与外部样本一致 |
| 四 | 按行为族验证全干员、敌人、Boss 和活动机制 | 每个支持条目有配置来源、机制验收和证据；近似项与未验证项仍显式列出 |
| 五 | 按新范围补齐特殊模式与版本更新流程 | 每种模式有完整输入到终局测试；新版本生成差异清单并重跑对应验收 |

优先修正共用规则，再扩展条目。否则新增几百个技能也会继续受到同一个错误范围或属性公式影响，后续返工更大。

## 还差多少

可以确认的是：已有大部分通用系统的结构与大量数据，仍有至少十项本次确认的基础问题、两份缺失的养成数据、当前未通过的 45 项测试，以及六个需要继续建设或校准的领域。完整准确性没有外部验收分母，不能诚实给出“已经完成 80%”之类数字，也不能用 717 除以 762 代替准确率。

工作量应按目标分层理解。让限定版本的一组普通关卡、代表编队和已知机制达到可信，属于持续校准项目；让全部干员、敌人、Boss 和活动在边界组合下均与客户端一致，需要大量逐机制验证；再纳入特殊模式则会扩大状态与输入模型。

**工程判断，非测量工期**：在一名熟悉代码的开发者、目标版本数据可取得、真实战斗样本可持续提供的前提下，基础修正与首批对照样本宜按数周规划，较广的普通战斗可信覆盖宜按数月规划，全量机制和特殊模式宜按多个人月甚至更长规划。先完成前两个阶段，测量每个行为族的修复与验证成本，再估算剩余时间，比现在承诺一个完成日期更可靠。

若目标是可靠的 AI 打图，应先公布清楚的支持范围：限定版本、关卡、编队与机制经过对照，其余条目显示近似或未验证。让策略依赖的结果有证据，比仅扩大“能加载”的关卡数量更接近完整模拟。
